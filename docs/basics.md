# skill 编写原则

本文件只回答两个问题：**为什么这么做**、**什么算合格**。

具体怎么做不在这里——骨架怎么搭、质量门怎么跑，见 `skill-draft`；正文怎么写给 agent 看，见 `writing-for-agents`。三份文件分工明确，不互相复制。

## 怎么读这份文件

条目分三档：

- **硬规则**：违反即为不合格。审核按它逐条判，判据写在条目里。
- **建议**：默认这么做；偏离要能说出理由。
- **反模式**：出现过就说明设计有问题。单独列出来，是为了能在最早的时候认出来。

## 边界

### 硬规则

1. **先判边界，再动笔。** 三个问题都要答「是」：这件事会反复发生吗？需要经验判断吗？值得固化吗？
   判据：说得出它在什么场景下会被第二次、第三次调用。
2. **一个技能只做一件事。**
   判据：能用一句话说清它解决哪一类任务，且这句话里不出现「并且」。
3. **不重复已有能力。** 工具能直接做的，不包一层技能；始终生效的规则放配置，不放技能。
   判据：技能里没有任何一步是某个已有工具的原样转发。

### 建议

- 定位说不清时，先当成一次性任务做一遍；出现第二次再固化。
- 技能之间可以引用，但不要复制别人的正文——那会造出两份真源，迟早不一致。

### 反模式

- 为一次性任务建技能包。
- 把「始终生效的项目约定」写进技能，指望它每次都被触发。

## 结构

### 硬规则

1. **`SKILL.md` 是唯一必需的文件。** `scripts/`、`references/`、`assets/` 按需创建，不建空目录。
2. **`references/` 里的每个文件都必须被正文指向。** 没人引用的参考文件等于死代码。
3. **正文长度是软门槛：5000 token / 500 行。** 超线不禁止，但要在文末写明为什么不能拆；超得越多，理由要越硬。
4. **开头标明技能类型。** 三选一：约束型（管调性）、流程型（管工序）、混合型。当前多数是混合型。
   类型决定审核重点——约束型看禁止清单与边界，流程型看步骤与完成标志。
5. **不写机器本地绝对路径，不写工具版本号，不写死环境路径。** 路径与版本一律运行时解析。
   判据：把整包复制到另一台机器，不改一个字就能跑。
   「机器本地」指随机器变化的位置（家目录、本机上的工程目录）。**平台标准位置不算** ——
   Windows 的 `C:/Windows/Fonts` 同平台通用，能否跑取决于平台而不是哪台机器；质量门只扫家目录，
   正是在守这条边界。
6. **包内脚本只用标准库。** 别人装不上第三方库，质量门也就跑不起来。

### 建议

- 可选项、题库、文案外置成 `assets/` 下的数据文件，正文只写流程与判据；增删选项只改数据文件。
- 参考文件按「什么时候需要读它」命名，而不是按内容归类。

### 反模式

- 把长规格全塞进 `SKILL.md`，或者反过来把步骤全塞进 `references/`。
- 在仓库根新建 `ruff.toml` / `ty.toml` / `rumdl.toml` 来放宽规则——等同于关掉质量门。

## 触发

### 硬规则

1. **`description` 只有一个读者：模型。** 它在会话启动时被注入系统提示词，是模型决定调不调用这个技能的唯一依据。
   写给它看，不是写给用户看。
2. **必须带触发分支与触发词。** 写清「什么情况下用我」，并附上用户真会说的词，中英文都算。
3. **单段，短。** 一句话能力加一串触发词。它每个会话都在系统提示词里占位，越长越吃亏。
   参考刻度 **300 字符**，**是建议值、不做硬判** —— 该多长本就随触发分支数变化，卡成门禁只会
   逼人砍掉必要的分支。
4. **frontmatter 只写 `name` 和 `description`。** 不要 `title`（会被规则当成文档标题，把正文的一级标题降级），不要展示用字段，不要版本号。
   例外：平台要求的字段保留（如 `agent_created`、`disable-model-invocation`）。
5. **`name` 必须等于目录名。** 不等就不加载。

### 建议

- 触发词集中写在末尾，用固定引导写法（如「触发词：…」/「Triggers: …」），方便整串替换。
- 写完拿一个**不该触发**的场景对照一遍；会被误触发，说明 `description` 写宽了。

### 反模式

- `description` 写成产品介绍，没有任何触发分支——技能永远不会被调用。
- 用额外的展示字段（多语言名、可见性、版本号）补信息，指望宿主或模型会读它们。

## 写作

### 硬规则

1. **每个步骤一个完成标志。** 步骤用动词开头；「做完了」必须有可判定的判据（退出码 0、零告警、文件存在、某项对得上）。
2. **正面描述与禁止清单组合使用。** 只说「要什么」会漏边角；只说「不要什么」会让模型失去方向。
3. **解释要简练。** 冗余说明会稀释核心指令的权重——模型记住的是密度最高的那句。
4. **给方向，不给参数。** 写清判断依据与边界，把具体数值留给运行时决定。

### 建议

- 命令一律可复制，包在代码块里，不要写成散文。
- 篇幅不够时先砍形容词，保住命令与判据。

### 反模式

- 步骤只有描述、没有完成标志，「做完」由模型主观裁量。
- 把整段推理过程写进正文，读者读完仍不知道下一步做什么。

## 验证

### 硬规则

1. **每个包都要有可一键跑通的脚本化自检。** 至少覆盖三件事：包内一致性（文档与代码是否对得上、`name` 是否等于目录名）、真实数据的往返、对外部规范或基线的比对。
2. **踩坑点单独成节，与检查清单并列。** 信息密度最高的部分往往不是流程说明，而是踩坑点；位置统一才找得到、才加得进去。
3. **踩坑点「发现一个加一个」。** 遇到一次就补一条，不攒。
4. **改完必须重跑。** 改文件后不重跑质量门就交付，等于没过门。

### 建议

- 踩坑点写成「现象 → 原因 → 对策」三段，方便别人核对是不是同一条。
- 提前想「出错了怎么办」：开头检查输入，失败时给出可执行的下一步，而不是只报一句错。
- 准备一条「不该触发」的场景对照 `description`。只有正例时，`description` 越写越宽也不会有人喊停；反例是可选项，但它是唯一能在事后抓住误触发的办法。
- 测试用例三要素：一条指令（模拟用户怎么说）、输入（如果需要）、期望结果（好的输出大致长什么样）。

### 反模式

- 门禁报错就去关规则，而不是修问题。
- 踩坑点散落在正文各处，或者只留在提交信息与聊天记录里——它们会消失。

## 编排

### 硬规则

1. **说清中间产物与暂停点。** 派活时写明：产出什么、落在哪个路径、在哪个点停下来等人拍板。
2. **控制主上下文。** 让子任务只回「文件路径 + 一句话摘要」，不要把全文倒回主会话。
3. **保留人工检查点。** 关键节点（大纲、方案、验收）停下来让人拍板，比全自动跑到底质量更高。

### 建议

- 三种组合方式按需选：并联（快、多方向同时试）、串联（上一步的产物是下一步的输入）、循环（质量不达标就打回重做）。
- 需要独立上下文或要限定工具时用子智能体；同一份材料要多个视角时，先并联再汇总。

### 反模式

- 派活不说暂停点，全流程一把跑完才给人看。
- 让每个子任务都把完整正文回吐给主会话——上下文会被中间产物吃光。

## 硬规则速查

审核时按这张表逐条判，判据回到对应小节的条目。

| 分组 | 条数 | 一句话判据 |
| :--- | :--- | :--- |
| 边界 | 3 | 三问都是「是」；一句话说得清；不转发已有工具 |
| 结构 | 6 | 无空目录、无死链引用、无写死路径；开头标了类型 |
| 触发 | 5 | `description` 单段带触发词；frontmatter 只留必需的键 |
| 写作 | 4 | 每个步骤都有完成标志 |
| 验证 | 4 | 自检能跑通；踩坑点单独成节 |
| 编排 | 3 | 说清中间产物与暂停点；留人工检查点 |
